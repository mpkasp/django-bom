# Material List Performance Improvement Plan

## Objective

Reduce the time required to navigate between pages of the material list rendered by `home()` in `bom/views/views.py`. Pagination currently takes more than five seconds in production.

Target outcomes:

- Page navigation under 500 ms where practical, and under one second at normal production load.
- Search and material filters under one second where practical.
- No N+1 queries.
- No behavior changes to latest-revision selection, seller selection, pricing, search, print, export, authorization, or organization isolation.

## Evidence From the Codebase and Database Dump

Relevant files:

- `bom/views/views.py`
- `bom/list_queries.py`
- `bom/models.py`
- `bom/templates/bom/dashboard.html`
- `bom/helpers.py`
- `bom/tests/test_bom.py`
- `bom/tests/test_performance.py`
- `perf/README.md`

The production dump contains approximately:

- 1 organization
- 480 parts
- 594 part revisions
- 4,073 manufacturer parts
- 453 seller parts
- 663 assemblies
- 3,520 subparts and assembly/subpart relationships
- 48 sellers

This dataset is not large enough by itself to explain five-second pagination. The likely causes are inefficient query shape, repeated database work, recursive BOM cost calculation, production database plans, or infrastructure latency.

The existing performance baseline records roughly 1,015 home-page queries before earlier optimization and roughly 110 after the recorded `stage-a` optimization. The current test still permits up to 200 queries for `home`, which is too high for a 25-row page and should be reduced after the implementation.

## Current Hot Paths

### Latest revision query

`home()` first evaluates all matching part IDs into a Python list, then constructs a latest-revision subquery. It later reconstructs the revision query after search filtering. This creates unnecessary work and duplicates query-building logic.

### Pagination count

`Paginator` issues a `COUNT(*)` query. The count may be expensive because it operates over a latest-revision query with joins and ordering. Measure it separately before changing pagination behavior.

### Seller selection

`paginate_part_revs()` prefetches manufacturer parts and seller parts, then computes an optimal seller in Python. The template calls `part.optimal_seller` again. Verify that the attached cache is always used and that no fallback query occurs.

### Unit cost

The template renders `part_rev.bom_unit_cost`. For assemblies this may recursively walk the BOM. The property is cached per object, but nested BOM traversal can still be expensive if it causes queries or substantial Python work.

### Autocomplete

Autocomplete is disabled by default, but when enabled the view iterates through all matching revisions and all manufacturer parts and serializes the complete dictionary into every HTML response. This work occurs before pagination and should be moved to a separate endpoint if the feature is needed.

## Phase 1: Establish a Production-Like Baseline

1. Measure these requests separately:

   - `/`
   - `/?page=2`
   - `/?page=10`
   - `/?product=0`
   - `/?product=1`
   - `/?q=<common-term>`
   - `/?page=2&q=<common-term>`

2. Record total wall time, database time, query count, response size, and database CPU/load.

3. Add temporary timing instrumentation around:

   - `PartClassSelectionForm`
   - base `parts` queryset construction
   - search filtering
   - latest-revision queryset construction
   - autocomplete generation
   - `paginate_part_revs`
   - seller prefetch and optimal-seller calculation
   - template rendering

4. Capture the SQL generated by the slowest requests and run `EXPLAIN (ANALYZE, BUFFERS)` on PostgreSQL.

5. Measure the paginator count separately. Determine whether time is spent in the count, page query, prefetch queries, Python processing, or template rendering.

Do not add indexes or rewrite queries based only on assumptions. Keep before/after plans and timings.

## Phase 2: Refactor the Home Query

### 1. Keep part IDs lazy

Replace the eager operation:

```python
part_ids = list(parts.values_list("id", flat=True))
```

with a queryset/subquery such as:

```python
part_ids = parts.values("id")
```

or use `parts.values("id")` directly in the revision filter. This avoids materializing all IDs in Python.

### 2. Apply filters before selecting latest revisions

Refactor `home()` into one query-building path:

1. Resolve organization and form state.
2. Create `Part.objects.filter(organization=organization)`.
3. Apply part-class filtering.
4. Apply search filtering.
5. Select the latest revision for the resulting parts.
6. Apply `product=1` or `product=0` material filtering.
7. Apply stable ordering.
8. Handle download, print, or pagination.

Do not build one latest-revision query and then rebuild it after search.

### 3. Preserve and document latest-revision semantics

The current code treats the greatest `PartRevision.id` as the latest revision. Verify this is the intended domain rule before changing it. If it is correct, retain it and optimize the query. If timestamp is the true rule, use `timestamp DESC, id DESC` and update tests deliberately.

### 4. Add a unique ordering tie-breaker

Retain the existing human-facing sort order and add `part_id` or `part_revision_id` as the final key:

```python
.order_by(
    "part__number_class__code",
    "part__number_item",
    "part__number_variation",
    "part_id",
)
```

This prevents rows from moving between pages when sort values are equal.

### 5. Investigate the count query

First optimize the underlying query. If count remains a major cost, evaluate:

- A count-friendly queryset.
- Counting matching parts rather than materialized revision rows where equivalent.
- Short-lived organization/filter-specific count caching.
- Removing exact totals from the UI in favor of next/previous navigation, only if product requirements allow it.

Do not remove exact counts without checking `bom/templates/bom/ui/pagination.html`.

## Phase 3: Make Seller Data Explicitly Page-Local

1. Inspect the `Prefetch` graph in `bom/list_queries.py` and verify that it covers every seller and manufacturer access used by the dashboard.

2. Use explicit prefetched attributes where practical:

   - manufacturer parts attached to each part
   - seller parts attached to each manufacturer part
   - sellers selected on each seller part

3. Compute the optimal seller once per displayed part.

4. Attach the result to the row object, for example:

```python
part_rev.list_seller = seller
```

5. Update `dashboard.html` to use the prepared value rather than calling `part.optimal_seller` again:

```django
{% with part=part_rev.part seller=part_rev.list_seller %}
```

6. Add a query-capture test proving that rendering page 1 and page 2 does not issue a seller query per row.

7. Ensure `Part.optimal_seller()` never enters its fallback query path during dashboard rendering.

Do not move the seller-selection algorithm into complex SQL unless profiling proves Python selection is still expensive after prefetching. The dump contains only 453 seller parts, so correct bulk prefetching should be sufficient initially.

## Phase 4: Handle BOM Unit Cost

1. Profile pages containing only raw materials, only assemblies, and mixed rows.

2. Confirm whether `bom_unit_cost` causes additional queries during normal dashboard rendering.

3. Ensure nested BOM traversal uses prefetched data and does not issue queries per node.

4. If recursive computation is the main remaining cost, choose one of these approaches:

   - Short term: compute once per row and attach a prepared display value.
   - Medium term: optimize and bulk-prefetch the BOM graph.
   - Long term: store a denormalized calculated cost per revision/currency and invalidate it whenever seller pricing or BOM inputs change.

5. Preserve the current distinction between raw-material seller cost and assembly BOM cost. Add correctness tests before introducing denormalized values.

## Phase 5: Remove Full-Catalog Autocomplete Work

Keep `enable_autocomplete=False` by default.

If autocomplete is required:

1. Add a separate authenticated JSON endpoint, for example `/search-autocomplete/?q=...`.
2. Scope every query to the current organization.
3. Require at least two or three characters.
4. Return only 10–20 results.
5. Debounce browser requests.
6. Use `select_related` and `values()`/`values_list()` for a small response.
7. Cache common results briefly with organization-scoped keys.
8. Remove full dictionary generation and JSON embedding from the normal dashboard request.

Test that enabling autocomplete does not cause unbounded catalog iteration on every paginated page.

## Phase 6: Add Indexes Based on PostgreSQL Plans

Evaluate candidates only after capturing query plans:

```text
bom_partrevision (part_id, id DESC)
bom_partrevision (part_id, material, id DESC)
bom_part (organization_id, number_class_id, number_item, number_variation, id)
bom_sellerpart (manufacturer_part_id, minimum_order_quantity)
```

The latest-revision index is the first candidate to investigate. The material index is useful only if product/raw-material filtering is frequent and the plan benefits from it.

For `icontains` search, existing B-tree indexes are generally insufficient. If PostgreSQL search is slow, evaluate `pg_trgm` plus GIN/GiST indexes on:

- `bom_partrevision.searchable_synopsis`
- primary manufacturer-part number
- manufacturer name, if needed

For every index:

1. Capture the before plan.
2. Add a migration.
3. Run `ANALYZE`.
4. Capture the after plan.
5. Compare execution time, rows scanned, buffers, sorting, and index usage.
6. Check migration time, storage, and write overhead.

Do not add speculative indexes that are not used.

## Phase 7: Reduce Row and Template Work Carefully

The dashboard uses only a small subset of the `PartRevision` fields. After query-count tests exist, evaluate `only()` or `defer()` for fields not needed by the table and its properties.

Potentially required fields include:

- revision ID and part ID
- description
- revision
- material
- configuration
- assembly ID
- part number fields
- organization ID
- part class code/name
- primary manufacturer-part relationship if used by the selected cost path

Be cautious: deferred fields accessed by model properties can create hidden queries. Keep the change only if it reduces total work.

Where useful, prepare transient list-row values in Python:

- `list_part_number`
- `list_seller`
- `list_unit_cost`
- `list_category_name`

Do not duplicate business logic without tests.

## Phase 8: Evaluate Pagination and Caching

### Offset pagination

Measure pages 1, 2, 10, and 50. Five seconds on page 2 with roughly 480 parts is unlikely to be caused by offset alone. Implement keyset pagination only if latency grows substantially with page number.

Keyset pagination requires stable ordering, cursor values in pagination links, and a query that filters after the last row instead of skipping rows. It may require a stable annotated/materialized sort key because the current order includes joined fields.

### Current revision modeling

If latest-revision selection remains expensive at larger scale, consider adding a current-revision relationship on `Part`, a constrained current flag, or a read-model table. This is a long-term change and should not be the first optimization for the current dump size.

### Caching

Cache only safe, organization-scoped data. Potential targets are part-class choices, autocomplete results, or short-lived counts. A full-page cache must account for organization, role, language, currency, CSRF behavior, and catalog-version invalidation. Add caching only after query and N+1 problems are fixed.

## Tests and Acceptance Criteria

Add or update tests for:

- page 1, page 2, and stable ordering
- latest revision selection
- part-class, product, and raw-material filters
- all supported search sources
- empty results
- seller and unit-cost display
- print and CSV/XLSX export
- admin-only controls and deletion behavior
- multi-organization isolation
- no per-row queries

Extend `bom/tests/test_performance.py` with a larger production-like dataset. Run it against PostgreSQL as well as SQLite; only PostgreSQL timings represent production.

After optimization, target:

- fewer than 15 queries for a normal paginated home page, subject to measured required queries
- query count independent of page row count
- no query count growth caused by seller or BOM depth
- page 1 and page 2 under one second in production-like PostgreSQL conditions
- pagination materially below the current five-second behavior
- unchanged search, filtering, cost, print, export, authorization, and tenancy behavior

## Recommended Delivery Order

### Stage A: Measure

1. Capture timings, query counts, and PostgreSQL plans.
2. Separate count, page query, prefetch, Python, and template time.
3. Record a baseline in the existing performance tooling.

### Stage B: Fix query construction

1. Remove eager `part_ids` materialization.
2. Apply all part filters before latest-revision selection.
3. Use one query-building path.
4. Add deterministic ordering.
5. Add query-count regression tests.

### Stage C: Fix page-row preparation

1. Make seller prefetch explicit.
2. Attach and render one prepared seller per row.
3. Verify no seller N+1 queries.
4. Profile BOM cost calculation.

### Stage D: Isolate optional work

1. Keep autocomplete off by default.
2. Move autocomplete to a limited, authenticated endpoint if needed.
3. Remove full-catalog serialization from the dashboard path.

### Stage E: Optimize PostgreSQL

1. Add only plan-supported indexes.
2. Add trigram search indexes only if search plans justify them.
3. Re-run the production-like benchmarks.

### Stage F: Address remaining bottlenecks

1. Optimize or denormalize BOM costs if proven necessary.
2. Consider current-revision modeling at larger scale.
3. Consider keyset pagination or safe caching only when measurements justify them.

## Implementation Constraints

- Do not change the meaning of latest revision without confirming the domain rule.
- Do not use PostgreSQL-only ORM features unless PostgreSQL is the supported production database.
- Do not cache data without organization and permission isolation.
- Do not denormalize costs before proving recursive calculation is a bottleneck.
- Do not optimize only for the supplied 480-part dump; preserve scalability.
- Do not remove pagination totals without checking the UI requirement.
- Do not trust template caching implicitly; make prepared row values explicit.
- Do not claim success from SQLite-only timings.
